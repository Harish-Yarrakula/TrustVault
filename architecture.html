How TrustVault works

A visual guide to the browser, API, database, and private services—and how a document moves through them safely.

User workflows

Architecture at a glance

1. Browser

React and Vite app, published as static files.

  • Shows authorized workspace features.
  • Sends API requests with the session cookie.
  • Uploads file bytes to storage using a short-lived form.

2. TrustVault API

FastAPI backend behind HTTPS.

  • Authenticates users and checks tenant membership.
  • Enforces document ownership, grants, expiry, and share status.
  • Verifies uploads before making documents available.

3. Data services

Private services used by the backend.

  • PostgreSQL stores users, grants, sessions, and audit events.
  • Private S3-compatible storage holds document bytes.
  • ClamAV scans uploads over a private network.
Browser ⇄ API: HTTPS requests; access checks happen on the server

Connected services

Amazon SES sends invitation and verification emails.

Object Lock archive stores audit copies when production archive configuration is enabled.

Two separate deployments

The frontend static site and backend service are built and deployed independently. The browser reaches the API through the configured HTTPS host or same-origin proxy.

Trust boundary

The browser is not trusted to decide access. Hidden buttons and client-side filters are for usability only; the API remains authoritative.

Workflow: upload a document

1. Create recordBrowser sends filename, size, type, and checksum to the API.
→
2. Get upload formAPI checks the user and returns short-lived storage instructions.
→
3. Upload and verifyBrowser sends bytes to private storage. API checks signature, size, checksum, and malware scan before marking the document ready.

Why upload directly to storage? Large file bytes do not need to pass through the API server. The API still controls who can start an upload and whether the uploaded object becomes available.

Workflow: open a document

1. RequestBrowser asks the API for the document.
→
2. AuthorizeAPI checks the current user, tenant, ownership or active grant, and document state.
→
3. Return bytesOnly after approval does the API read private storage and return the file.

Key rule: a document ID, admin role, category, or visible UI control is not permission to read file bytes. The API checks access for each request.

Other important workflows

WorkflowHow it works
Named permissionAn owner grants one user READ or WRITE on one document. Expiry and revocation are checked by the API; category folders do not inherit grants.
External invitationThe invitation is emailed through SES. The external client activates an account and receives READ-only access to specifically granted documents.
Share linkThe API checks expiry, revocation, limits, and configured passcode/OTP requirements. A share link is a bearer credential; send it only to its intended recipient.
Audit eventThe API records relevant activity in PostgreSQL's per-tenant audit chain. When configured, an immutable archive copy is written and verified.
AI access suggestionThe system records a recommendation only. A human owner must approve before a permission is created.

Deployment and operations

PartDeployment responsibilityImportant configuration
FrontendBuild and publish static assets to the frontend host.VITE_API_URL; optional VITE_S3_UPLOAD_ORIGIN.
BackendRun the API behind a TLS reverse proxy. Do not expose the application port directly.PostgreSQL credentials, signing key, allowed hosts and origins, storage, scanner, and email configuration.
Private servicesKeep document storage private; expose ClamAV only to the backend network.Least-privilege cloud IAM, bucket policy, scanner health, and archive retention.

Availability note: the API, database, object storage, malware scanner, email service, and optional audit archive are separate dependencies. Failures can prevent the related workflow; security checks should not be bypassed to make it appear successful.
