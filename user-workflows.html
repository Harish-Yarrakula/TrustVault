TrustVault workflows

A secure document workspace with per-document grants, expiring external access, and an auditable trail. This guide maps what each user does and what TrustVault sends by email.

Architecture and data flows

Roles and access model

ADMIN

Workspace administrator

Invites and manages tenant members, reviews analytics and audit history, and manages document permissions. Administrator role alone does not grant access to every file's contents. Admin MFA is required.

MEMBER

Document owner or colleague

A member owns documents they upload. Owners manage their files and grants. Other members need an active named READ or WRITE grant on that particular document.

EXTERNAL_CLIENT

Invited external recipient

Accepts an invitation, sets a password, signs in, and can read documents explicitly granted to them. External clients are read-only.

LINK RECIPIENT

Secure-link recipient

Uses an expiring, optionally passcode- and OTP-protected link to download a shared document. This is distinct from an authenticated company-member grant.

Important: category folders organize the workspace but do not inherit permissions. Authorization is checked by the API for each document operation.

Member uploads and grants access

  1. Sign in. An administrator must first create/invite the corporate member. Admin accounts enroll in TOTP MFA.
  2. Upload a document. Select a PDF, PNG, or JPEG and choose a category. The browser sends bytes to private object storage using a short-lived presigned upload request.
  3. Server verifies the upload. TrustVault checks size, SHA-256, actual file signature, declared MIME type, and ClamAV scan. Failed checks or unavailable scanning prevent the document from being served.
  4. Choose recipients. Grant an existing company member READ or WRITE access to this document, or invite an external recipient for READ access.
  5. Recipient accesses only the grant. The API checks the current account and document grant before returning bytes. Revocation or expiry blocks future API reads.
  6. Review activity. The owner and administrator can see relevant notifications; administrators can review audit history and workspace analytics.
Result: access applies to an individual document, not every file in its category folder. A removed grant does not invalidate a copy already downloaded by the recipient.

Administrator invites a company member

  1. Open role/settings management and enter the member's email address.
  2. TrustVault sends an invitation email with an acceptance link. The default invitation lifetime is seven days.
  3. The invitee opens the link and activates their account by setting a password.
  4. The administrator manages roles, checks dashboard activity, and reviews audit records. Grant document access separately; admin membership does not automatically grant file-content access.

Email subject: “You have been invited to TrustVault”. Delivery uses Amazon SES and requires a configured sender, region, and authorized recipient in the SES account.

Owner invites an external client to one document

  1. From document access management, choose “Invite by email” and enter the recipient's email.
  2. Choose READ. The backend rejects WRITE for an external-client role. The invitation and associated grant default to a seven-day expiry.
  3. TrustVault sends the invitation email. The link leads to the acceptance page; the recipient sets a password and activates the account.
  4. The external client signs in and sees only their explicitly granted document. The owner can revoke the grant; administrators can revoke the guest account.

Email subject: “You have been invited to TrustVault”. If SES delivery fails, the operation reports failure instead of presenting an invitation as successfully sent.

Owner creates a secure share link

  1. Open Share for a document you own. Choose expiry; optionally enter a recipient email and passcode. Email OTP requires a recipient email.
  2. TrustVault creates a random token and stores its hash, not the raw token. Link expiry and maximum download count are enforced by the backend.
  3. Send the copied link only to the intended recipient. A link is a bearer credential: anyone who obtains it may attempt to use it until it expires or is revoked.
  4. If a passcode is set, the recipient must enter it. If OTP is required, the recipient enters the six-digit code from email before downloading.
  5. The owner can revoke the share link. Subsequent server requests using that link are denied.

Email subjects: “A TrustVault document was shared with you” and, when OTP is enabled, “Your TrustVault verification code”. Each OTP is valid for ten minutes; five failed attempts trigger a temporary lock. A recipient can request up to three replacement codes per ten minutes. Both emails go to the named recipient.

Do not forward the OTP or share URL to support/chat. If a link is exposed, revoke it and create a new one.

Security and audit expectations

  • Every document operation must be authorized server-side; changing an ID or calling an endpoint directly must not bypass the check.
  • Revocation prevents future server-mediated reads. It cannot erase copies already downloaded.
  • Audit events are hash chained and archived to Object Lock storage in production. Administrators can run integrity verification.
  • Known audit limitation: cookie-only or invalid-identity failures are not comprehensively attributable.
  • Keep database, S3, SES, signing-key, MFA, and invitation secrets out of screenshots, browser shares, logs, and documentation.
